# Route Grapher — Solution / Architecture / Algorithm

> 給一個目標圖形，在真實街道上生成一條可騎的單車路線，從地圖上看起來像那個圖形。

這份文件描述**目前跑在 `server/app.py` 上的東西**。每個常數後面盡量附上它是怎麼來的
—— 量出來的、擬合出來的、還是拍腦袋的，因為這個專案裡最貴的錯誤全都出在「以為量過了」。
逐條的失敗紀錄在 `docs/BACKLOG.md`。

---

## 1. 一次請求走過的路

```
輸入：圖案名稱 + 目標公里數 + 地點(lat,lon) + 模式(bike/walk) + variant
  │
  ├─ 0  快取查詢          _ROUTE_CACHE → _routes.db          命中就結束（見 §7）
  │
  ├─ 1  量街道尺度         street_scale.scale_for()           這個地方的街有多疏
  ├─ 2  定尺寸            feasibility.plan()                 公里數 → 圖形寬度 + 取樣點數
  ├─ 3  載入路網          network()                          region 拼接 / OSM 下載 / 磁碟快取
  │
  ├─ 4  粗掃描            coarse_scan()                      幾萬個(中心,旋轉)，秒級
  ├─ 5  挑候選            select_candidates()                非極大值抑制 → 6 個放置點
  ├─ 6  精配              refine() → fit_route()             ★ Viterbi 地圖匹配，每個候選一次
  ├─ 7  排序與去重        wander/excursion 門檻 → shape_distance
  │
  └─ 8  輸出              GPX + WGS84 座標 + 街道背景 + 辨識度說明
```

第 1–2 步的**順序是刻意的**。街道尺度決定圖形要畫多寬，寬度決定要載入多大的路網
——所以先載路網再量尺度是把因果倒過來。它曾經就是倒的：信義區的使用者先等 58.5 秒
下載一個用全國預設尺度算出來的路網，再等 35.7 秒下載探測用的路網，然後整個重算。

## 2. 核心演算法：把理想曲線當成 GPS 軌跡來做 map matching

這是整個專案的技術核心（`routeshape/matching.py`）。

### 2.1 問題形式

把目標圖形沿**弧長**等距取樣成 n 個點 `p_1 … p_n`（閉合）。要在街道圖 G 上找一條
封閉路徑，依序經過 n 個路口 `x_1 … x_n`，使得：

```
total =  Σ_i  w_i · ‖p_i − x_i‖                          ← emission：貼合誤差
      +  Σ_i  max(0, len(path(x_i → x_{i+1})) − ‖p_i − p_{i+1}‖)   ← 多繞的距離
      +  Σ_i  10 · mean_dist(path(x_i → x_{i+1}), 理想曲線)         ← 偏離形狀
```

三項單位都是公尺，所以可以直接相加。索引在 `i = n` 時繞回 1 —— 路線必須閉合。

這就是 **map matching**（HMM/Viterbi 版本，Newson & Krumm 那一支），只不過被匹配的
不是一條 GPS 軌跡，而是一條合成出來的目標曲線。

### 2.2 為什麼不能各點各自找最近路口

POC 1 就是那樣做的，結果證明它做不到唯一重要的那個取捨：

> 一個離輪廓 60 m 但在通行街道上的路口，通常遠勝於一個離 20 m 但必須繞 300 m
> 才到得了的路口。

各點獨立決定就看不到這件事，因為代價發生在**兩點之間**。

### 2.3 三個構件

**(a) 沿弧長取樣，不是沿參數 t。** 參數化的心形在側翼跑得快、在尖端跑得慢，等 t 取樣
會把點全堆在尖端。那是反過來的：側翼好走、尖端難走，把樣本擠進難處什麼也買不到。

**(b) 每個點保留 k 個候選路口，而不是一個。**
`build_candidate_sets()`，k = 10，半徑 260 m，且**排除 degree ≤ 2 的節點**（死路只能原路
折返）。半徑外的候選丟掉以免 DP 跑掉，但最近的那個永遠保留，所以沒有點會無路可選。

半徑可以是一個數，也可以是**每個輪廓點一個**。這點很重要：只調 emission 的
*價格* 幾乎量不出差別，因為在 142 m 的街格上用 260 m 半徑，DP 只有大約兩個街區的
自由度，根本沒有交易空間。**自由度才是槓桿，不是價格。**

**(c) Viterbi 動態規劃選一組。** `viterbi_closed_loop()`。

### 2.4 閉環怎麼處理

一般 Viterbi 處理開鏈。這裡是環：最後一點必須接回第一點，而那個選擇取決於起點是誰。
做法是把**第一點釘在它的每個候選上各跑一次完整 DP**，取最便宜的完整環。k 個候選就是
k 趟 —— 夠便宜，所以選擇「精確」而不是「聰明」。

### 2.5 那個 deviation 項是整段的關鍵

只用長度算成本，DP 會去**抄近路**：截掉曲線的一個彎更短，而沒有任何項在為「離開形狀」
收費。`_path_deviation()` 把路徑加密到每 20 m 取樣，量它到理想曲線的平均距離，乘以
`DEVIATION_WEIGHT = 10.0`。

**這一項才讓 DP 是 shape-aware 而不只是 efficient。**

### 2.6 計算量（為什麼慢）

| 量 | 大小 |
|---|---|
| 輪廓點 n | 30 – 200（由 §4 決定） |
| 每點候選 k | 10 |
| transition 要算的 Dijkstra | **n × k** 次（每步、每個來源候選一次） |
| Viterbi | k 趟 × n 步 × k² |
| 每次請求的放置點數 | 最多 6 |

所以一次請求最壞是 `6 × 200 × 10 = 12,000` 次 Dijkstra。這是主要成本，詳見 §8。

## 3. 放在城市的哪裡：兩階段搜尋

搜尋空間（中心 × 旋轉）遠大於能跑完整匹配的數量，所以分兩階段（`routeshape/placement.py`）。

### Stage 1 — 粗掃描，只問一個便宜的問題

**「這條理想曲線附近到底有沒有路面？」** 完全忽略連通性。

- 對整張路網每 15 m 沿邊取樣，建一棵 k-d tree（`build_street_index`）
  —— 取樣**邊**而不是節點很關鍵：台北路口間距 100–200 m，只索引節點的話，一條
  完美跑在街區正中央的輪廓會被判定離街道 80 m。
- 中心格點間距 200 m，旋轉 12 個角度（每 30°）。
- 分數：`mean + 0.5 × p95`，輪廓上任一點離街道 > 250 m 就直接判死。

p95 那項是用來把「整圈均勻偏 30 m」（沒關係，匹配器吸收得掉）和「四分之三完美、
沿河那段偏 200 m」分開。只看平均會把兩者評成一樣，但形狀不會。

向量化：同一旋轉下對所有中心一次 broadcast query，所以幾萬個放置點只要幾秒。

### Stage 2 — 精配

`select_candidates()` 做**貪婪非極大值抑制**，彼此至少 700 m，取 6 個
—— 相鄰格點分數幾乎一樣，單純 top-n 會把同一個街角回傳六次。

每個候選跑一次完整的 §2 匹配器。連通性、繞路、折返全部在這裡才被定價。
有些放置點跨過一條沒有橋的河，`NoRouteFoundError` 是搜尋一整座城市的正常結果，不是 bug。

### 提早停止

`variant == 0` 時，一旦某個候選同時滿足 `wander ≤ 0.30`、`excursion ≤ 0.08`、
且 `recognition.as_good_as_rated(shape, excursion)`，就停止不再試其他放置點。

依據是 POC 24：從 3 個放置點增加到 6 個，shape distance 只動 0.008–0.009，而人能
看出差別的最小幅度是 0.10 —— 大約是最小可見變化的十二分之一，卻要等兩倍的時間。

`variant ≥ 1`（使用者按「換一個位置」）不提早停止，因為那時需要搜到別的答案可以給。

## 4. 公里數怎麼變成圖形尺寸

`routeshape/feasibility.py`。這段最不直覺，但它決定了圖案像不像。

### 4.1 推導

```
W_min = n_min × s / P        最小可用寬度
D     = P × W × detour       寬度 W 的圖形會產生多長的路線
D_min = n_min × s × detour   周長 P 消掉了
```

**周長消掉了。** 一個圖形的最短可走距離只取決於三件事：它需要幾個輪廓點、
當地街格的特徵尺度、以及網路強加的繞路係數 —— 跟輪廓多長無關。

### 4.2 `n_min`：離線算，不碰地圖

把圖形用 n 個點取樣，和用 4000 點取樣比較 `shape_distance`，找出損失穩定低於 0.05 的
最小 n。

實作上要對付兩種雜訊：多邊形在頂點數的倍數上會被**完美重建**（曲線掉到 0 再彈回），
而有重複細structure的圖形會**共振**（台北 101 的十六段模組在 176 點通過門檻，然後在
200、208、280、316 點又跳回去）。對曲線取**滾動中位數**同時解掉兩者。

### 4.3 `s`：街道尺度，是地點的屬性不是全國常數

`routeshape/street_scale.py`。定義是**方向性街道尺度**：沿一個選定方位走，到最近街道的
中位距離，對 12 個方位平均。

不是「到最近街道的距離」—— 那在台北是 19 m 而這個是 142 m，因為路線必須沿著一個方向
走，而大多數街道不往它要去的方向。前者在城市間跨度 3.5 倍，後者只有 1.6 倍。

POC 26 量了七個城市：板橋 141 m、基隆 223 m。基隆拿 280 m 的台北常數去要 10 km 的心形，
得到 15.0 km、shape distance 0.266，完全認不出來。**稀疏的城市需要實體上更大的圖形
才畫得出同一個圖。**

一個地方的尺度 = 全國常數 × (該地方向性尺度 / 台北的 142 m)。台北剛好落在原地，
九個 POC 的測量都還算數。量測固定用 5 km 的框，快取到 lat/lon 小數點後兩位（約 1.1 km）。

### 4.4 `detour`：不是常數

曾經是 1.25。POC 25 量了實際留下來的路線：

```
2.5 km 1.29   4.2 km 1.21   5.0 km 1.32   7.3 km 1.54   8.7 km 1.92
12.3 km 1.93  12.3 km 2.18  12.4 km 1.75  12.4 km 1.82
```

常數 1.25 對這九筆的殘差 sd 是 0.339，而且**平均誤差 +0.412** —— 它不只是散，它系統性地
低估，而低估的正是產品對使用者的承諾。50 km 的心形被報成 42.5–57.5 km，實測 72.2 km。

現在是寬度和街道尺度的線性函數：

```python
detour = 0.4544 + 0.0734 × width_km + 0.002079 × street_scale_m   # 殘差 sd 0.173
```

刻意是直線而不是更複雜的東西：九個點跨兩個圖形撐不起更多參數，而被取代的那個量只有
一個參數。

### 4.5 反解寬度

因為 detour 本身是寬度的函數，所以不能除，要解二次式：

```
P·b·w² + P·a·w − T = 0        w 單位 km
```

用固定 detour 去除，就是讓 50 km 的請求回來只有 22 km 的原因。

### 4.6 取樣幾個點

視窗從 `n_min`（足以代表這個圖形）到 `P × W / s`（超過就是街格滿足不了的約束）。
`WINDOW_FRACTION = 1.0`，也就是坐在上限 —— 讓錨點恰好一個街道尺度一個。

曾經是 0.75，三角形是反例：8 km 時給它 16 個錨點、相距 687 m，而街道尺度是 280 m，
錨點之間路線幾乎不受約束，得分 0.127（高於門檻），而**有使用者在任何測量之前就說了**。
同一個放置點改用 24 和 32 個錨點是 0.094 和 0.095。

## 5. 圖案從哪裡來

目前 `SHAPES` 有 **26 個**，五個來源：

| 來源 | 數量 | 模組 |
|---|---|---|
| 參數式（heart / star5 / crescent / triangle / trex） | 5 | `shapes/library.py` |
| 手繪 pack | 10 | `shapes/pack.py` |
| Emoji 描邊 | 11 | `shapes/openmoji.py`, `shapes/emoji.py` |
| 文字（「LOVE」「台北」） | 動態 | `shapes/multi_contour.py` |
| 自由文字描述 | 動態 | `describe.py` |

所有圖形都正規化成：有序點列、隱含閉合、以 bounding box 置中、**寬度剛好 1.0**。
只有放置時的 `width_m` 決定實際大小。

### Emoji 描邊
- **OpenMoji**（SVG）：`svgpathtools` 解析，取所有填色區域的聯集當主體，再貪婪地
  加上細節線條，只要加了之後輪廓還夠簡單。貼著剪影的細節環會被切掉貼合的那段、
  保留其餘作為開放線，否則剪影會被描第二次。
- **Noto Color Emoji**（點陣）：Moore-neighbour 追蹤。字型路徑是**探測**出來的
  （`find_font()`），不是寫死的 —— 寫死 Debian 路徑曾讓另一台機器上所有描邊失敗，
  而頁面只回「找不到披薩」，那是謊話。

### 多輪廓合併
`multi_contour.merge()` 把多個閉合輪廓接成**一條**閉合曲線：用最短連接線把各部分連起來，
走過每個輪廓一次，繞進鄰居再原路回來 —— 一筆不離紙。每條連接線走兩次，在地圖上是
一條細線。

這讓整個專案的其他部分**原封不動**適用：`shape_distance`、`n_min`、粗掃描、Viterbi
全都假設單一閉合曲線，沒有一個需要知道這條曲線本來是八片。參考模板用**同一條合併後的
曲線**建，所以路線不會因為騎了一條刻意要求的連接線而被懲罰。

### 自由文字 → 圖形
`describe.py`：**模型提議，測量否決。** Claude 畫出輪廓，`describe.check()` 決定它能不能騎，
失敗就帶著原因退回給模型。檢查項就是實際踩過的坑：自我相交（十二個手繪圖形裡有三個）、
不能有洞（一條閉合曲線做不到）、細節要花距離（`n_min × s × detour` 是地板）、
身分必須在輪廓裡（POC 20，不能是靠明暗辨識的東西）。

## 6. 指標：各自量什麼，各自能信到哪

| 指標 | 定義 | 用途 | 可信度 |
|---|---|---|---|
| `shape_distance` | Procrustes，對平移/縮放/旋轉/循環位移/方向都不變 | **搜尋的目標函數** | POC 5 有人類資料背書 |
| `wander` | `arclength(route)/arclength(template) − 1` | 門檻 0.30 | 方向可複製，**校準不可** |
| `excursion` | 最大偏離 / 寬度 | 門檻 0.08 | 方向對，但和 distance 相關 0.77 |
| `recognition` | 實測命名率 | 給使用者的文案 | ← 見下 |

### `shape_distance` 怎麼算

經典 Procrustes shape distance。關鍵是旋轉對齊**不用額外成本**：對角度最小化平方距離
有閉式解，把互相關的**實部變成模長**——

```
min_θ Σ|a_i − e^{iθ} b_{i+k}|² = Σ|a|² + Σ|b|² − 2|Σ a_i conj(b_{i+k})|
```

所以同一次 FFT 同時服務了所有循環位移和所有旋轉。

### 最重要的一個結論

POC 39 把這個專案收集過的**全部 316 個人類判斷**（5 輪、67 張圖）拿來做五折交叉驗證，
問哪個模型最能預測*下一個*答案。平均 held-out log-loss：

```
none                 0.6502
distance             0.6465     ← 出貨用的
excursion            0.6495
distance+excursion   0.6460
drawing              0.4850     ← 最好
drawing+excursion    0.4851
```

**distance 和 excursion 都一文不值** —— 全部落在「什麼都不知道」的 0.005 以內。
知道那是*哪張圖*則把損失砍掉 25%。POC 40 把「解析度地板」（一張圖有多少細節細於
街網能表現的尺度）丟進同一個測試，結果**正好落在 null 上**。

也就是說：**辨識度是圖畫的屬性，任何以距離為自變數的曲線，都比一張「人們實際說了什麼」
的表格更差。** 所以 `recognition.py` 現在是一張 26 列的實測表（命名了幾次 / 看過幾次），
用 Jeffreys 平滑，文案直接帶著次數，沒實測過的圖案就明說沒實測過。

## 7. 服務層

### 端點
| 端點 | 作用 |
|---|---|
| `GET /api/shapes` | 圖案清單 + 48 點縮圖輪廓 + 可行性 |
| `GET /api/places` | 起點清單 |
| `POST /api/search` | 中英文關鍵字搜 1266 個 emoji |
| `POST /api/describe` | 自由文字 → 新圖形 |
| `POST /api/plan` | 只算可行性，不碰地圖，立即回 |
| `POST /api/route` | 完整搜尋 |
| `GET /api/route/{id}.gpx` | 下載 |

### 三層快取

```
_networks       記憶體   路網。key=(lat,lon,mode,half_size)
                        ★「已載入的更大的框可以用」——同心更大的正方形必然包含小的
_ROUTE_CACHE    記憶體   完整答案。key=(shape,km,mode,lat,lon,variant)
_routes.db      SQLite   同上，但存活過重啟
```

**路網大小的重用規則寫在兩個地方**，因為只有記憶體那份時，重用只活在一個 process 裡：
重啟會重新下載一座硬碟上已經有的城市。`network.cached_covering()` 補上了磁碟那一半。

### Store 的設計（`server/store.py`）

- **存路線，不存圖片。** 一個答案 1,068 KB，其中 1,045 KB 是 `streets`（畫在路線後面的
  16,433 條道路折線）。那是路網的 bbox 過濾結果，所以讀出來時重建，從不寫下。
  剩下 22 KB。1,500 條路線是 33 MB 而不是 1.6 GB。
- **指紋才是重點。** 每一列都帶一個輪廓的 hash（重採樣 64 點、四捨五入到小數 4 位）。
  圖形被重畫過的列在載入時直接丟掉。齒輪在兩輪評測之間長出了中心孔，導致同一個名字
  下是兩張不同的圖，污染了評分池好幾週（BACKLOG 45）—— 這個設計讓那類 bug 在這裡
  不可能發生。

### 「換一個位置」
搜尋沒有隨機成分，重算會回傳一模一樣的路線。使用者要的是**不同的地方**，而搜尋本來
就配了好幾個。variant 1 是第二好的。

去重要做兩次（`rank_fits`）：先**按路線本身**（兩個相距 700 m 的中心仍可能貼到
同一組路口），再**排除已經給過這位使用者的**（variant 0 提早停止、variant 1 搜完
六個，兩次排序的集合不同，齒輪的「六個裡第二好」正好就是提早停止已經給過的那一個）。

路線的身分 `route_mark()` 取自**存下來的 WGS84 座標**，不是投影後的幾何，也不是
`hash()`。兩個理由，都是踩過的坑：`hash()` 對 bytes 的結果每個 process 都不一樣
（PYTHONHASHSEED），而這個值會寫進資料庫再跨 process 比對；而取自投影幾何的話，
已經存在資料庫裡的 76 條路線無法重算自己的 mark。取自座標則是「從這一列自己算出來」，
不需要 migration。見 BACKLOG 56。

### `--precompute`
把 26 個圖案 × 4 個預設距離（10/30/50/100 km）全部填進資料庫。**大的先跑**，
這樣最寬的那個下載最大的框，其餘全部重用。單一工作失敗不會拖垮整批。

## 11. 測試

```bash
python -m unittest discover -s tests -t .      # 全部，約 5 秒
python -m unittest tests.test_matching -v      # 單一模組
```

標準函式庫的 `unittest`，沒有 pytest，因為整套測試必須在一份乾淨的 checkout 上
跑得起來，不需要裝任何產品本身不需要的東西。

**沒有任何一個測試碰網路。** `tests/gridfixture.py` 在記憶體裡建一個曼哈頓格狀路網，
這比下載一座城市**更快也更嚴格**：在規則格網上，兩個路口之間的最短路徑長度就是
曼哈頓距離，所以測試可以斷言一個算術答案，而不是「上次程式回傳了什麼」。

承重的那個案例：**四個角都落在格點上的正方形有一個完美解，而匹配器找得到它** ——
繞路 1.0003、零折返、shape distance 剛好 0.0。BACKLOG 54 的 matcher 重寫就拿這三個
數字當 oracle。

| 檔案 | 蓋到什麼 |
|---|---|
| `test_metrics.py` | `shape_distance` 的五種不變性、`excursion`、`wander`、`alignment_angle` |
| `test_matching.py` | 候選集、transition 成本（格網上是純算術）、Viterbi、端到端 oracle、河流阻斷 |
| `test_feasibility.py` | 尺寸的來回一致性、樓地板、`plan` 的拒絕 |
| `test_shapes.py` | 全部圖案的共同契約、弧長取樣、多輪廓合併的長度恆等式 |
| `test_placement.py` | 放置變換、街道索引、粗掃描評分、非極大值抑制 |
| `test_ranking.py` | 排序與去重（「換一個」壞過兩次的那段） |
| `test_store.py` | 存取來回、指紋失效、withdrawn/重畫的圖案 |
| `test_network_cache.py` | 「更大的框可以用」在磁碟上那一半 |
| `test_server.py` | 快取鍵、街景框大小、文字圖案釘正、`/api/describe` |

測試斷言的是**性質**而不是存下來的數字，因為這個專案出過的錯從來不是 crash ——
指標拿旋轉過的參考去比所以看不見旋轉、store 用名字當鍵而五個圖案在同名下被重畫、
街景用常數決定大小。每一個都產生了一個看起來很合理的數字。

寫這套測試的時候，**修正了四個我自己的錯誤假設**（不是程式的 bug）：`alignment_angle`
回答的是「要把路線轉回去多少度」所以符號是負的；`resample_closed` 給的是等**弧長**
因此過彎處的弦長不等；`multi_contour.merge` 回傳的是三元組；`outline_for` 是以**平均**
置中而不是 bounding box。

順便找到一個真的 bug：`/api/describe` 的**成功路徑**會 NameError（`re` 沒 import）。
它從來沒被看到過，因為沒有憑證時 `propose` 會先丟例外、服務回報 unavailable，
在那三行之前就 return 了。

## 12. 讀這份文件的人最該記住的三件事

1. **核心是 map matching，不是畫圖。** 目標曲線被當成一條 GPS 軌跡，用 Viterbi 在
   街道圖上匹配。讓它 shape-aware 的是 transition 裡那個 deviation 項；沒有它，
   DP 會理性地抄掉每一個彎。

2. **尺寸決定像不像，比匹配器重要。** 周長在推導裡消掉了，剩下 `n_min × 街道尺度 ×
   繞路係數`。這三個量裡有兩個曾經被當成全國常數，兩次都是錯的。

3. **辨識度沒有幾何預測子。** 316 個人類判斷說：shape_distance、excursion、
   解析度地板，預測力都等於零。搜尋仍然用 shape_distance 當目標（它得排序某個東西），
   但對使用者講話時，講的是實測表裡的次數。
